## 2. Findings

### Open findings

### [MEDIUM] Interrupted payment creation has no provider reconciliation path

- Location: `services/payment.service.js:226-283,336-556`; `models/paymentCreation.model.js:42-63,73-75`; `tests/services/payment.test.js:400-450,680-756`
- Category: Race condition and workflow enforcement | CWE-362, CWE-841 | OWASP A06:2025 Insecure Design; OWASP API6:2023 Unrestricted Access to Sensitive Business Flows
- Confidence: High (95%)
- Problem: Payment creation now claims `{user, idempotencyKey}` before contacting the provider and correctly blocks concurrent duplicate calls. However, a claim can remain `processing` indefinitely when the provider accepts the request and the process stops before `Payment.create`, when the provider response is ambiguous, or when local persistence fails after the external effect. The replay path returns `processing` whenever no local payment exists and never leases, expires, retries, queries, or reconciles that claim.
- Evidence: `createPayment` persists a processing claim at lines 435-443, calls the external provider at lines 474-482, and stores the local payment only at lines 493-549. `resolveCreationClaim` returns `processing` at lines 258-265 when no payment is present. The model has a status/update-time index but no recovery ownership or reconciliation state. The regression test at lines 400-425 explicitly proves that such a claim remains in progress and that the provider is not called again. Stripe receives a stable server-derived provider idempotency key, but no code uses it to retrieve or reconcile a prior outcome; ZarinPal has no equivalent native idempotency mechanism in this integration.
- Impact: An accepted provider operation can be orphaned from local state, and the client can be permanently unable to complete or safely reuse that logical request. This can strand checkout authorities, create support-only recovery, and leave application and provider records inconsistent. The current flow creates payment intents rather than capturing funds, which limits the present financial impact.
- Fix: Add an explicit reconciliation state machine for stale processing claims. Record enough non-secret provider correlation data to query a prior outcome, lease recovery work atomically, and reconcile to `succeeded`, `failed`, or a visible manual-review state. Never blindly repeat a non-idempotent provider call. Add fault-injection tests for interruption after provider acceptance and before local persistence, plus ambiguous transport failure tests for each provider.

### [MEDIUM] Single-factor password policy accepts easily guessed passwords

- Location: `validators/password.validator.js:1-55`; `validators/register.validator.js:41-63`; `validators/passwordResetConfirm.validator.js:57-83`; `validators/passwordChange.validator.js:36-61`
- Category: Weak password requirements | CWE-521 | OWASP A07:2025 Identification and Authentication Failures
- Confidence: High (98%)
- Problem: Password-only login is supported, but the shared validator accepts eight-character passwords and checks only six hard-coded common values. Registration, reset, and change all inherit this policy.
- Evidence: `validatePassword` rejects only values shorter than eight, entirely numeric values, six listed strings, or bcrypt inputs over 72 UTF-8 bytes. An eight-character dictionary mutation that is not one of those six values passes every password-setting path.
- Impact: Guessable credentials are more likely to succeed during password spraying or credential reuse and are substantially easier to recover from a stolen password-hash database. Online throttling does not protect an offline copy of the hashes.
- Fix: For password-only authentication, raise the minimum to 15 characters while retaining a usable bcrypt-safe maximum. Check the complete candidate against a large, refreshed compromised-password corpus through a reviewed local data file or a privacy-preserving range API with an explicit outage policy. Keep the policy centralized and avoid arbitrary character-class composition rules.

### [MEDIUM] CI executes actions and a service image through mutable tags

- Location: `.github/workflows/ci.yml:20-35,45-64`
- Category: Software supply-chain integrity | CWE-494, CWE-829 | OWASP A03:2025 Software Supply Chain Failures
- Confidence: High (100%)
- Problem: Both jobs execute `actions/checkout@v7` and `actions/setup-node@v7`, and the MongoDB job starts `mongo:8.0`. These are mutable references that can resolve to different code without a repository diff.
- Evidence: The workflow pins neither action to a reviewed full commit SHA nor the MongoDB image to a digest. The dependency lockfile and `npm ci` do not verify workflow actions or container-image tags.
- Impact: A substituted upstream artifact can execute in the runner, read repository contents and available credentials, alter test results, or poison produced evidence.
- Fix: Pin every action to a reviewed full commit SHA and retain the release tag in a comment. Pin the MongoDB image by digest. Update these references through reviewed dependency-update changes.

### [LOW] Security-sensitive account events have no durable audit trail

- Location: `services/login.service.js:12-53`; `services/passwordReset.service.js:285-363`; `services/passwordChange.service.js:107-174`; `services/emailChange.service.js:362-417`; `services/accountDeletion.service.js:49-100`; `middlewares/errorHandler.middleware.js:26-35`; `middlewares/requestId.middleware.js:1-10`
- Category: Insufficient logging | CWE-778 | OWASP A09:2025 Security Logging and Alerting Failures
- Confidence: High (95%)
- Problem: The API creates request IDs and records unexpected errors, but it has no centralized durable event path for authentication successes/failures/lockouts, password resets or changes, email changes, account deactivation, or authorization denials. Repository-wide searches find startup, development mail-preview, worker-failure, and exception logs, but no security-event model or monitored sink.
- Evidence: The security-sensitive services complete their state transitions without writing an actor-attributed audit event. The centralized error handler records unexpected exceptions only. The account-email worker's structured failure metadata is operational logging, not a durable security history.
- Impact: Credential stuffing, targeted lockouts, account takeover, and malicious security-setting changes may be difficult to detect promptly or reconstruct reliably after an incident.
- Fix: Add a centralized structured security-event path that records event type, outcome, stable user identifier when known, server-issued request ID, trusted source signal, and time without passwords, tokens, mail bodies, or unnecessary PII. Cover login results and lockouts, password/email changes, recovery completion, account deactivation, and authorization denial. Send records to a monitored append-oriented sink and alert on targeted, distributed, decisive, and missing-source signals.

## 3. Worth checking

These items depend on deployment or external components not present in the repository and are not counted as confirmed findings.

1. Reverse proxy and client IP: `middlewares/requestThrottle.middleware.js:28-35` keys limits on `req.ip`, while `app.js` does not configure Express `trust proxy`. Verify the exact proxy/load-balancer topology, which hop overwrites forwarded-address headers, and whether distinct clients reach the service with distinct trusted addresses. A shared proxy address can let one client exhaust limits for everyone; an overly broad trust setting makes addresses spoofable.
2. Canonical origins and TLS: `config/environment.js:48-65,119-138` accepts HTTP and HTTPS for token-bearing frontend links and the ZarinPal callback. Verify that non-local deployment rejects HTTP and that TLS is enforced at the edge. `controllers/notification.controller.js:27-52` builds pagination links from the request host; verify the edge overwrites `Host`, or return relative/configured-origin links.
3. Deactivation versus erasure: the `/delete` route is documented as account deactivation, and `services/accountDeletion.service.js:49-87` retains account and related data. Confirm the product's retention and erasure obligations. If callers are promised deletion, add a distinct authenticated erasure workflow with per-store completion records.
4. Device-token transfer: `services/deviceToken.service.js:36-57` permits an authenticated caller that possesses an existing globally unique device token to rebind it to another user. Confirm with the push provider and client design that token possession is intended to authorize ownership transfer and that notifications never carry sensitive data. No push-delivery implementation is present to establish the downstream impact.
